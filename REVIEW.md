# Правила ревью

- **Статус:** действует
- **Дата:** 2026-11-18
- **Для кого:** агент-ревьюер PR (`.github/workflows/opencode-pr.yml`, скилл
  `code-review`) и человек-ревьюер.

Правила бронирования, которые ревьюер проверяет по диффу. Источник истины —
[спецификация](docs/spec/calendar.md); здесь — выжимка для ревью, при
расхождении выигрывает спецификация. Механику (формат, линтер, типы,
контракт и SDK) ревьюер не повторяет — за это отвечает `mise run check`.

## 1. Инварианты бронирования

Каждое нарушение — находка с обязательным форматом из §4.

1. **Источник констант — один.** `TIME_ZONE`, `WORKDAY_START/END`,
   `SLOT_STEP_MINUTES`, `BOOKING_WINDOW_DAYS` живут в
   `apps/api/src/config/calendar.ts`. Фронтенд не дублирует их, а получает
   через API. Найденный в коде литерал `30`, `18:00`, `14`, `Europe/Moscow`
   вне конфига — находка.
2. **Время — только UTC-инстанты** ISO 8601 с `Z` на границе API. Сетка,
   рабочие часы, границы окна и группировка по дням считаются в
   `Europe/Moscow` (UTC+3, перехода на летнее время нет). Границы окна
   проверяются по московской дате, не по UTC. Перевод времени через
   `new Date(...)` со смещением без учёта пояса — находка.
3. **Текущее время — только `Clock`-провайдер** (ADR-0003). Прямой
   `Date.now()`/`new Date()` в доменной логике API — находка; тесты
   не должны зависеть от даты запуска.
4. **Полуоткрытые интервалы `[start, end)`.** Пересечение:
   `slotStart < bookingEnd && bookingStart < slotEnd`. Касание границами —
   не конфликт: 10:00–10:30 и 10:30–11:00 совместимы. Использование
   `<=` на любой из сторон сравнения — находка.
5. **`end` брони не принимается от клиента.** Длительность берётся из типа
   встречи, иначе клиент может подделать интервал. Поле `end` в запросе
   на бронирование — находка.
6. **Старт — только на сетке:** 09:00–18:00 по Москве, шаг 30 минут,
   встреча заканчивается не позже 18:00 (последний старт: 17:30 для 30 мин,
   17:00 для 60 мин). Других стартов нет, включая 09:00 в UTC «по совпадению».
7. **Окно записи — 14 дней:** сегодня и 13 следующих по Москве. Старт
   `<= now` или за пределами окна — ошибка `slot_out_of_window`. Прошедшие
   слоты не попадают в ответ вообще (ни `free`, ни `taken`); пустой список
   на сегодня — норма, не ошибка.
8. **Порядок проверок бронирования фиксирован** — от него зависят тесты:
   форма → тип встречи (`404`) → окно (`400 slot_out_of_window`) → сетка
   (`400 slot_out_of_grid`) → пересечения (`409 slot_taken`). Перестановка,
   меняющая код ответа хотя бы в одном кейсе, — находка.
9. **Проверка пересечений и вставка брони — в одной критической секции**
   мьютекса по дате (ADR-0003). Проверка без мьютекса или мьютекс не по дате
   — находка: при конкуренции должен успевать ровно один запрос.
10. **`id` брони генерирует сервер** (`crypto.randomUUID()`); клиент его
    не задаёт. `id` типа встречи, наоборот, задаёт владелец; сервер не
    генерирует id типа.
11. **Ошибки — единый конверт** `{ code, message }` с машинночитаемым кодом
    из §10 спецификации. Проверяется только код, не текст сообщения.
12. **Список владельца** `GET /api/bookings`: предстоящие брони (старт не
    раньше `now`), сортировка по `start` по возрастанию, все типы в одном
    списке, без пагинации.
13. **Идемпотентности нет:** повторная бронь того же слота — `409`.
    Защита от двойной отправки — `isSubmitting` на фронтенде; её снятие —
    находка.

## 2. Вне объёма проекта

Находкой не является отсутствие: авторизации, отмены/переноса брони,
пагинации, уведомлений, хранения между перезапусками, `PATCH`/`DELETE`
типов встреч, `Idempotency-Key`. Предложение «а хорошо бы добавить…» —
не ревью-вывод; фиксировать только как явный отход от объёма, если дифф
притворяется, что это в объёме.

## 3. Что ревьюер не повторяет

- Форматирование, ESLint, типы, сборку, контракт→SDK — `mise run check`.
- Соответствие ответов JSON-схеме, негативные коды, тест конкуренции —
  контрактные e2e (§13 спецификации).
- Сквозной сценарий гостя и владельца — браузерный E2E Playwright.

Достаточно ссылки на прогон CI; дефекты механики ревьюер не описывает.

## 4. Формат находки — обязательные поля

Каждое замечание содержит все четыре поля, без исключений:

| Поле               | Что указать                                                                                                                                     |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **Файл**           | путь относительно корня репозитория                                                                                                             |
| **Строка**         | номер строки (или диапазон) в текущей версии файла                                                                                              |
| **Условия ошибки** | входные данные или ситуация, при которых код срабатывает неверно; если нужен невоспроизводимый контекст (время, конкуренция) — описать его явно |
| **Последствие**    | наблюдаемое поведение для пользователя или контракта: неверный код ответа, потерянная/просочившаяся бронь, сломанная сетка и т.п.               |

Без любого из полей находка не публикуется. Гипотезы формулировать только
с пометкой, что поле «условия ошибки» не установлено; подтверждённые
дефекты и гипотезы не смешивать.
